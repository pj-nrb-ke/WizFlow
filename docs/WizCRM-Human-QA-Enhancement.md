
# WizCRM Human-Centric QA Enhancement Review & Instructions

## Review of QA Reports (001 & 002)

The QA reports generated by Cursor demonstrate strong progress in technical auditing and structured testing. The reports are well organized and show clear improvement between QA-001 and QA-002.

Key strengths identified:

- Better issue tracking structure in QA-002
- Improved technical validation
- Better API and backend coverage
- Security-focused improvements
- Pagination and UI state handling improvements
- More mature regression validation
- Better documentation discipline
- Introduction of Playwright-based testing
- Better handling of retries and fixes

However, the reports still reveal a major weakness:

Cursor is primarily behaving like:
- a code auditor
- a backend engineer
- an API validator
- a technical QA engineer

instead of:
- a real office worker
- a receptionist
- an impatient sales rep
- a confused HR officer
- a distracted user
- a non-technical end-user

This means the current QA process is still too "engineering-centric" instead of "human-centric".

The reports contain:
- heavy backend observations
- technical findings
- API-driven validations
- structured code analysis

But they lack:
- true frontend human emulation
- workflow confusion analysis
- chaotic user behavior testing
- browser interaction abuse
- long-session fatigue testing
- realistic navigation testing

The QA process must now evolve from:
"Can the code work?"
to:
"Will real humans break this app?"

Technical QA: 7.5 / 10

--------------------------------------------------
CRITICAL DIRECTION CHANGE
--------------------------------------------------

The next QA cycles MUST focus heavily on:

HUMAN FRONTEND EMULATION TESTING

Cursor must test the app primarily through:
- real browser interaction
- visual navigation
- frontend workflows
- simulated human behavior

instead of primarily relying on:
- code inspection
- API-only testing
- backend validation

--------------------------------------------------
MANDATORY FRONTEND TESTING REQUIREMENT
--------------------------------------------------

IMPORTANT:

Conduct the MAJORITY of testing through REAL browser interaction using:
- Playwright
- Cypress
- Puppeteer

The testing must emulate REAL NON-TECHNICAL USERS.

Do NOT rely mainly on:
- source code inspection
- backend-only analysis
- direct database validation

Use the frontend UI as the PRIMARY testing surface.

Backend inspection should ONLY be used when necessary for validation.

--------------------------------------------------
REQUIRED HUMAN-LIKE TESTING BEHAVIOR
--------------------------------------------------

Simulate realistic office users including:

- impatient users
- distracted users
- non-technical users
- careless users
- power users
- multitasking users

Examples of required human behavior simulation:

- random clicking
- repeated clicking
- double clicking
- rapid button spamming
- incomplete forms
- abandoning workflows midway
- browser refresh during save
- opening multiple tabs
- switching tabs repeatedly
- logout during transaction
- browser back button abuse
- refresh during upload
- network interruption during save
- rapidly changing pages
- resizing browser repeatedly
- mobile rotate during submission
- copy-pasting massive text
- uploading invalid files
- entering malformed data
- opening forms and abandoning them

The goal is:
BREAK THE APP LIKE A REAL USER WOULD.

--------------------------------------------------
MANDATORY PLAYWRIGHT / CYPRESS REQUIREMENTS
--------------------------------------------------

Use Playwright or Cypress to:

- navigate the app visually
- click through workflows
- submit forms
- emulate browser usage
- emulate mobile usage
- simulate human interaction timing

Randomize:
- delays
- pauses
- click timing
- typing speed

This is important because real humans do NOT behave like bots.

--------------------------------------------------

- visual density

- visual consistency
- enterprise-grade appearance

--------------------------------------------------
WORKFLOW CONFUSION ANALYSIS
--------------------------------------------------

Identify areas where users may become confused.

Examples:
- unclear buttons
- unclear navigation
- hidden actions
- inconsistent naming
- too many clicks
- unexpected behavior
- unclear validation messages
- workflow dead ends

IMPORTANT:
Think like a normal office employee, NOT a developer.

--------------------------------------------------
LONG-DURATION REALISTIC TESTING
--------------------------------------------------

Simulate real office usage.

Examples:
- process 50+ records continuously
- continuous usage for 30+ minutes
- repeated navigation
- repeated saves
- repeated searches
- repeated filtering
- repeated uploads

Look for:
- memory leaks
- UI slowdown
- browser lag
- inconsistent states
- stale data
- session issues
- loading degradation

--------------------------------------------------
SESSION INTERRUPTION TESTING
--------------------------------------------------

Test:
- internet disconnect
- session expiry
- browser crash
- tab restore
- laptop sleep/wake
- mobile app background/resume
- reconnect after disconnect

--------------------------------------------------
ACCESSIBILITY TESTING
--------------------------------------------------

Validate:
- keyboard navigation
- tab order
- focus visibility
- accessibility labels
- screen reader friendliness
- color contrast
- responsive readability

--------------------------------------------------
BROWSER COMPATIBILITY TESTING
--------------------------------------------------

Test:
- Chrome
- Edge
- Firefox

Also test:
- desktop
- tablet
- mobile viewport

--------------------------------------------------
MANDATORY EVIDENCE COLLECTION
--------------------------------------------------

Capture:
